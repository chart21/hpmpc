\section{The all\_opt configurations on ImageNet}\label{sec:triad}

The artifact's single-batch 2PC configurations (\texttt{measurements/configs/artifacts/triad/2pc/single\_batch}) combine
the online optimizations of the protocol: six configurations, A2bits and reshared, each in the three use cases of
\cref{sec:setting}: UC1, weights known to none (\flag{A_KNOWN=0}); UC2, weights known to the model owner
(\flag{A_KNOWN=1}, here also known in preprocessing, \flag{MODELWEIGHTS_KNOWN_DURING_PREPROCESSING=1}); and UC3,
weights known to all (public weights). Each runs ResNet50 on one ImageNet image with the three adders
(\flag{FUNCTION_IDENTIFIER=87,187,287}) and with \flag{COMPRESS=0,1}: 36 builds. As in the configurations, the model and
the image are dummies (\flag{MODELOWNER=-1}, \flag{DATAOWNER=-1}); the runtime does not depend on their values.

\paragraph{Builds.} \emph{As given}: the configuration unchanged (hpmpc \texttt{161cf1d}); its conv triples use
CHEETAH's \texttt{HomConv2DSS}. \emph{Optimized}: the configuration plus every optimization of this report
(final code: hpmpc \texttt{92a2c0e}, ConvTriple \texttt{8d8f244}, flexNN \texttt{417f12b}; rounds 1--3 at hpmpc
\texttt{1421df0}): \flag{CHEETAH_CONV_PACKED=1} with the pipeline, \flag{CUT_FRACTIONAL_BITS_OPT=1},
\flag{ADDITIONAL_RELU_THREADS=24} (equal to the configuration's \flag{ADDITIONAL_GEMM_THREADS}, as the two share one
pool), 100,000-word buffers, and \flag{A2B_CONV_BAKE=1} for the A2bits configurations; everything
else of \cref{sec:he,sec:ot,sec:online} and of the rounds below is on by default (the communication-optimized output
repacking of round~4 is a separate variant); \cref{tab:triadflags} lists every switch. \flag{RNG_AHEAD=1}, part of the optimized set until this
last round, is left out: at the final code it saves the Zen~4 hosts about 0.04\s of online time (median over the 36
builds) but costs the Zen~3 hosts up to 0.17\s (UC3, \flag{COMPRESS=1}: 0.51 against 0.36\s); a profile puts that in
the online draws, most likely waiting for the ring's producer thread. Each
build runs three times per machine pair (median): the as-given builds alternating with the final code, the optimized
builds in a separate series.

\paragraph{Correctness.} The same flags on CIFAR-10 with the AdamW model and real data (P0 / P1 as owners, 10
images) classify 3--7 images correctly for every configuration with \flag{COMPRESS=0} at the final code (plaintext:
6), including all UC2 builds. The outputs change only where a change alters the randomness that the probabilistic
truncation sees (the bake's privacy fixes of rounds 4 and 7, P1's prescribed shares in UC2 A2bits in round~6); every
other change leaves all 18 output hashes as they were. \flag{COMPRESS=1}
evaluates the ReLU on bits 12--19 only (\flag{REDUCED_BITLENGTH_m=12}, \flag{k=20}). With \flag{FRACTIONAL=5} the
carry dropped from the 12 low bits flips the sign of activations below 128.0, and even the plain RCA build without any of
our changes classifies 0 of 10. It is a runtime setting only, and we keep it running rather than accurate. Its A2bits
builds aborted with the element-parallel levels: the A2B bake committed conv masks for 8 of the 32 slices, so most
outputs drew fresh masks. The bake now requires a full-width ReLU, and \flag{COMPRESS=1} runs the A2B unbaked.

The A2bits configurations \emph{as given} are not correct. They set \flag{A2B_ONLINE_OPT=1}, which precomputes the
A2B's secret operand $[c] = \mathrm{bool}(-\lambda)$ by a Boolean addition in preprocessing, but not the bake
(\flag{A2B_CONV_BAKE}), and without it the preprocessing pass generates the MSB adder's Beaver triples for the
Boolean addition's input while the online phase uses its output $[c]$. On CIFAR-10 with the AdamW model, the as-given
A2bits flags classify 0--2 of 10 images in all three use cases and every adder, as do the optimized flags without
the bake (same output hashes as as-given in UC3); with the bake they classify 3--6. The reshared configurations do not
use \flag{A2B_ONLINE_OPT} and classify 4--7 of 10 as given.

\paragraph{Why the bake remasks ReLU inputs.} A ReLU on $m = v + \lambda$ runs its MSB adder on $s_1 = \mathrm{bool}(m)$,
public, and $s_2 = \mathrm{bool}(-\lambda)$, secret, since $\mathrm{bool}(m) \boxplus \mathrm{bool}(-\lambda) =
\mathrm{bool}(v)$. \flag{A2B_ONLINE_OPT} computes $[c] = \mathrm{bool}(-\lambda)$ in preprocessing, from the parties'
$\mathrm{bool}(-\lambda_0)$ and $\mathrm{bool}(-\lambda_1)$ by a Boolean addition (31 levels of AND gates). Two facts fix
\emph{when} this can happen. The adder's Beaver triples are defined by the masks of its input wires, $[c]$ among them,
and are requested while the preprocessing pass walks the circuit. And that pass is a single non-interactive sweep that
fixes masks, sends one-way messages and records triple requests; the triples are generated in bulk afterwards. So $[c]$
cannot be computed inside the pass, which would need 31 interactive rounds mid-sweep. It cannot be computed after the
pass either, which is the as-given configuration: its triples then belong to a different mask. It must exist
\emph{before} the pass, and with it every ReLU input's mask $\lambda$.

The bake therefore commits the masks first. Each party $i$ fixes a mask $\ell_i$ per ReLU input before the pass, the
Boolean addition runs on $\mathrm{bool}(-\ell_i)$, and the pass then has to deliver every ReLU input under the mask
$\ell = \ell_0 + \ell_1$. How depends on the layer that produces the input:
\begin{itemize}\itemsep1pt
\item \textbf{A convolution or FC layer with secret weights} (UC1, UC2) ends with a message that re-masks its output
  under a mask each party draws: the party draws $\ell_i$ instead. With weights known in preprocessing, P1's triple
  share is chosen so that its truncated output mask is $\ell_1$; such masks lie in the SecureML truncation's image
  (top \flag{FRACTIONAL} bits zero), so P1 commits $\ell_1$ there, uniformly. In the CHEETAH ResNet50 layout 8.00 of
  the 9.01 million ReLU inputs come straight from a convolution (with BatchNorm fused into it).
\item \textbf{A residual sum} (0.80 million inputs): the addend computed last draws $\ell_i - \lambda'_i$, where
  $\lambda'$ is the other addend's mask, so that the sum carries $\ell$ (round~5). P1's masks in UC2 must lie in the
  image, which $\ell_1 - \lambda'_1$ does not for a free $\lambda'_1$; so P1 commits the other addend's mask $m_b$ as
  well (a convolution draws it as a PRF value in the image, a ReLU's outputs are committed anyway) and commits
  $\ell_1 = m_a + m_b$ for the sum, exactly the mask the local addition gives; the partner then draws $m_a$
  (round~6).
\item \textbf{A convolution with public weights} (UC3) is local, so its output mask is $W \ast \lambda_{\mathrm{in}}$, a
  linear function of the previous bit injections' masks; choosing those so that $W \ast \lambda_{\mathrm{in}} = \ell$ is
  a linear system over $\mathbb{Z}_{2^{32}}$ without a solution in general. But every ReLU input's mask is a function
  of the input's masks and the earlier bit-injection masks alone, so the pass first runs the network over the masks,
  with each ReLU recording its input masks and outputting committed bit-injection masks, then runs the Boolean addition
  on the actual masks, and then the real sweep (round~4). With secret weights the same mask-only forward lets the
  conv triples start before the pass (round~5).
\item \textbf{Every other producer} fixes $\lambda$ without such a choice: in UC1 and UC2 the stem's pooling, whose
  BatchNorm passes its output on (0.20 million inputs). Such an input is moved onto the committed mask: party $i$
  sends $\delta_i = \ell_i - \lambda_i$ in preprocessing, and online both parties add $\delta_0 + \delta_1$ to $m$,
  which gives $v + \ell$. Since $\ell_i$ is uniform and known only to party $i$, $\delta_i$ is a one-time pad of
  $\lambda_i$; the price is one ring element per value and party, in preprocessing only: 1.5\,MiB.
\end{itemize}
Each committed mask must mask exactly one value, or the public masked values and remask messages reveal
differences of secret values or masks; and a mask may lie in the truncation's image only where nothing the other party
sees is masked by it alone (UC2, where P0 forms the masked value from its own share).
Rounds 4, 6 and 7 below fixed four violations of the first version. In preprocessing
every ReLU input that its producer moved is checked against its committed mask. In the first version, UC1 and UC2
remasked 1.00 million inputs (7.7\,MiB) and UC3 all 9.01 million ($9.01\cdot 10^6 \cdot 2 \cdot 4$ bytes $= 69$\,MiB,
exactly what the round-3 builds sent more than the as-given ones); now UC1 and UC2 remask 0.20 million and UC3 none.

\paragraph{What the bake costs.} The reference is the same build with \flag{A2B_CONV_BAKE=0}: the as-given A2B, which runs
the same Boolean addition (after the pass) and computes wrong signs, but sends what an A2B without the bake sends. At
the final code on flare / polynize (three interleaved runs per build, all nine A2bits builds with \flag{COMPRESS=0};
with \flag{COMPRESS=1} the bake is off):
\begin{itemize}\itemsep1pt
\item \textbf{Communication.} The triple generation and the online phase send the same bytes with and without the bake,
  in every build. The preprocessing pass sends 0.80\,MB more in each direction in UC1 and UC2, the remask of the
  stem's 200,704 ReLU inputs (1.53\,MiB, 0.1\% of their 1.0--1.8\,GiB of preprocessing), and nothing more in UC3. So
  the bake is free in communication with public weights, and costs the stem's remask with secret weights; free there
  too would need the stem's pooling truncation (or its BatchNorm) to commit its output mask (\cref{sec:limits}).
\item \textbf{Preprocessing time.} With secret weights $-0.10$ to $+0.09$\s (UC1 0.05--0.10\s less, UC2 0.03--0.09\s
  more): the bake moves the Boolean addition from after the pass into the OT phase, next to the conv triples, and adds
  the commitment (and in UC2 P1's residual commitment). With public weights 0.06--0.16\s more: the mask-only forward,
  about 0.3\s of serial work, partly hidden.
\item \textbf{Online time.} 0.00--0.07\s \emph{less}: the baked A2B reads the committed $[c]$ directly, where the
  unbaked one retrieves the Boolean addition's outputs. A first measurement (round~6) had put the bake at up to 0.1\s
  more online and 0.2\s more preprocessing: the baked A2B prepared its values serially, and the commitment was
  derived on one thread; round~7 removed both.
\end{itemize}

\paragraph{Where the time went.} In a profile at hpmpc \texttt{aeab3ae} (before the last two changes below), preprocessing
was bound by OT generation: in a CPU profile over all threads, ferret's LPN step took 31--44\%, the MITCCRH key
schedules 8--11\% and MPCOT 10--13\%. Per A2bits RCA inference the OT packs' setup cost 0.9\s, the bake's Boolean
addition 1.5\s (31 carry levels over 9.0 million values; one level pays a ferret extension of all 32 packs), the conv
triples 0.7\s and the network's preprocessing pass 0.5\s; PPA4 added 3.1\s of Beaver tuples. 84\% of the online CPU
samples were idle workers: RCA's 1,714 rounds at about 0.3\ms each are close to its floor, and disabling the NIC's
interrupt coalescing, which cut the ping from 0.25 to 0.08\ms, shortened the RCA online phase by only 7\%.
\Cref{tab:triadphases} shows the final code.

\paragraph{Changes.}
\begin{itemize}\itemsep1pt
\item \textbf{Worker wake-ups.} Between two circuit levels a worker spun about 100\,\textmu s and then slept on a
  futex, shorter than a round trip, so every level woke 24 threads. Workers now wait about 20\ms, on the counter's own
  cache line: with the counter next to the completion count, every completion invalidated the line for all spinning
  workers, which slowed the Zen~3 hosts' UC3 builds by up to 35\%. On AMD CPUs the wait uses
  MONITORX/MWAITX, which parks the thread on the cache line without taking issue slots from its SMT sibling.
\item \textbf{Vectorized GEMM accumulation} (\flag{A_KNOWN=1}). The online GEMM called a share-level kernel per
  multiply-accumulate on $\{m, \lambda\}$ structs, about 0.2 MAC per cycle. The kernel of each variant is a sum of plain
  ring products, so it now runs as $C = XY^\top$ on \texttt{uint32} matrices with a register-blocked $4\times 32$
  kernel (AVX-512 or AVX2), with the weight operand cached across a layer's calls. The results are bit-identical; with
  weights known in preprocessing, P1's accumulation, which its mask/send never reads, is skipped. The conv layers'
  online time falls by a quarter on Zen~3; on Zen~4 the accumulation was not on the critical path.
\item \textbf{The A2B bake} is restricted to full-width ReLUs (above).
\item \textbf{Conv triples alongside the preprocessing pass} (\flag{CHEETAH_CONV_ASYNC}). The conv triples used to
  start after the pass, whose single thread fixes their input masks. Now the batched HE pipeline starts on its own thread
  together with the pass and takes each layer as soon as the pass has recorded its masks; the rest of the preprocessing
  waits for it before the next generator uses the channels. Only the layers the pass reaches last leave a tail.
\item \textbf{Parallel preprocessing levels} (\flag{STREAM_PARALLEL_PRE}). The A2B, adder and bit-injection levels of
  the pass run on the worker pool like online. The pass's append-only streams (triple types and triple inputs, the
  pre-send buffer, stored outputs) get per-worker cursors, reads use the online cursors, and every worker's use of each
  stream is checked against the first element's. The GEMM levels stay serial. Both changes leave all 18 CIFAR-10 output
  hashes and two multi-batch hashes unchanged.
\end{itemize}
More HE/OT threads help the OT-heavy builds: \flag{CHEETAH_THREADS=64} instead of the configurations' 32 (64 OT packs)
shortens preprocessing by 8\% (median) on Zen~4 and 4\% on Zen~3, by up to 20\% for PPA4, but lengthens it by up to 30\%
for the UC3 RCA builds, where setting up 64 packs costs more than it saves. Two ferret threads per pack,
busy-polling the receive path and 31 instead of 24 workers did not help.

\paragraph{Results.} \Cref{fig:triad} shows all 36 builds; \cref{tab:triad} summarizes them. At the final code every
build is faster than as given online, on both pairs, and in preprocessing all but two UC3 builds with
\flag{COMPRESS=1} on Zen~3, which take 1--2\% longer (1.88 against 1.86\s and 2.01 against 1.97\s): rounds 4--7 did not
change their code, and the difference is within the run-to-run spread of these 2-second runs. In UC1 and UC2 the packed, pipelined and concurrent
conv triples with the exact wire format (since round~5 alongside the OT phase) cut preprocessing from 11.7--17.3\s to 1.7--5.5\s on the Zen~4 pair ($2.9$--$7.1\times$) and from
15.1--21.9\s to 2.7--6.9\s on the Zen~3 pair ($3.0$--$6.0\times$). The online phase falls from 0.77--1.55\s to
0.34--0.63\s ($2.0$--$3.0\times$; Zen~3: 0.72--1.73 to 0.24--0.63\s, $2.2$--$4.2\times$). In UC2, with the weights
known in preprocessing, the online phase takes 0.34--0.56\s on Zen~4 and 0.24--0.48\s on Zen~3.

UC3 needs no linear-layer triples, so its preprocessing is OT-bound and changes least: $1.1$--$1.2\times$ faster
($0.98$--$1.1\times$ on Zen~3), with the online phase $1.5$--$2.2\times$ faster ($1.4$--$2.2\times$ on Zen~3). Before the parallel
preprocessing levels, the Zen~3 hosts' A2bits builds with \flag{COMPRESS=1} preprocessed 0.11--0.14\s \emph{slower} than
as given (five interleaved runs each). A one-flag-off ablation placed all of it in \flag{ADDITIONAL_RELU_THREADS}, whose
per-call stream-cursor checks slowed P0's last preprocessing step from 0.32--0.34 to 0.44--0.49\s. Unchecked versions
for the preprocessing share removed that but slowed the \flag{COMPRESS=0} builds by as much, a code-layout effect we
did not keep. The parallel preprocessing levels now more than make up for it. As-given A2bits also skips the A2B bake and is not correct (Correctness).

\paragraph{Round 4.}\label{sec:triadround4} Four further changes; the measurements in rounds 4--6 are from flare /
polynize, the rerun of all 36 builds at the final code (\cref{tab:triad,tab:triadphases}, \cref{fig:triad,fig:triadcomm})
from both pairs.
\begin{enumerate}\itemsep1pt
\item \textbf{P1's bake in the pass.} The conv triples of reshared PPA4 did not run at half speed next to the pass:
  they waited for P1, whose pass took 1.28--1.43\s against P0's 0.38--0.50\s. P1 bakes the reshare bits into every
  conv output mask in the (serial) GEMM level, and with \flag{CUT_FRACTIONAL_BITS_OPT} the PPA4 slice ranks were
  recomputed for each of the 32 slices of each of the 7.3 million outputs. With the ranks fixed at compile time P1's
  pass takes 0.55--0.66\s, and reshared PPA4 preprocesses in 5.5--5.7\s instead of 6.0--6.4\s (UC1 and UC2), with the
  same outputs bit for bit.
\item \textbf{Privacy of the bake.} The committed masks are addressed by the next A2B's position, and every
  convolution took them. So the downsample convolution and the one after it masked their outputs with the same masks
  (1.5 million values: the differences of secret activations were public), and at the residual ReLU the remask
  message $\ell_i - \lambda_i$ gave away the downsample convolution's mask, since $\ell_i$ had also masked its
  partner. And the committed masks replayed the generator stream the passes then drew their own masks from. Now only
  a convolution feeding a baked ReLU takes committed masks, the others draw fresh ones, and the committed values come
  from a separate stream. Neither change costs traffic or time; the results of rounds 1--3 stand.
\item \textbf{UC3 bake for free.} The mask-only forward described above: UC3 A2bits sends 69\,MiB less in
  preprocessing (546 to 478\,MiB for RCA, 1{,}002 to 933 for PPA4, $-$7 to $-$13\%) in the same time (3.52--5.82
  against 3.54--5.92\s), and its online phase gets slightly faster (0.56--0.64 against 0.63--0.68\s), since no ReLU
  input is moved. In preprocessing every ReLU input's mask is checked against the mask-only forward's; none of the
  49 ReLUs differs.
\item \textbf{Output repacking}, the communication-optimized variant (\flag{CHEETAH_CONV_REPACK=1},
  \cref{sec:heformal}): 285 instead of 479\,MiB per HE product, preprocessing traffic $-$18 to $-$31\% in UC1 (1{,}229--2{,}150
  to 845--1{,}766\,MiB) and $-$11 to $-$24\% in UC2 (790--1{,}710 to 598--1{,}518\,MiB), for 1.3--1.7\s more
  preprocessing; the online phase is unchanged.
\end{enumerate}

\paragraph{Round 5.}\label{sec:triadround5} Two more changes.
\begin{enumerate}\itemsep1pt
\item \textbf{Conv triples alongside the OT phase.} During the OT phase only about 20 of the 64 hardware threads are
  busy (sampled every 50\ms), while the conv triples ran with the pass and after it. Every ReLU's outputs now take
  committed masks (values of a PRF under the party's key, by position), so every convolution's input masks are known
  before the pass: the pass first runs the network over the masks, where each convolution records its triple's
  inputs and stops, then starts the conv triples on four channels of their own, runs the OT phase (moved into the
  pass), and then the real sweep, which checks every convolution's inputs against the recorded ones. With all 32
  threads the conv triples slowed the OT phase down by about as much as they gained, with 16 throughout they became the
  tail of the Zen~3 builds with short OT phases (up to 0.7\s slower); they now take 16 while the OT phase runs and all
  32 after it. Against round~4 on Zen~4 preprocessing takes 0.03--0.34\s less over the 12 UC1 and UC2 builds; over all
  36 builds, the round-5 code preprocesses a median 0.15\s faster than round~3 on Zen~4 (up to 0.8\s) and 0.03\s on
  Zen~3, where a few builds with short OT phases are up to 0.11\s slower. The online phase gets 0.02--0.07\s faster,
  since the bit injections no longer draw masks.
\item \textbf{Residual sums baked.} The layer computed last of a residual sum's two addends draws $\ell - \lambda'$,
  where $\lambda'$ is the other addend's mask, so that the sum carries $\ell$. In UC1 this removes the residual sum's
  remask (6.1\,MiB); in UC2 P1's masks must lie in the SecureML truncation's image, so P1 still sent its half alone
  (3.1\,MiB saved; round~6 removes the other half). The outputs are unchanged bit for bit. In preprocessing, every baked ReLU input's mask is checked
  against its committed mask; the check showed that with dummy weights P1 holds a bias mask that the UC2 bake cannot
  compensate, so P1's A2B inputs were off after biased convolutions in the dummy-weight ImageNet runs (the timing
  measurements are unaffected).
\end{enumerate}

\paragraph{Round 6.}\label{sec:triadround6} In UC2, P1 now also bakes the residual sum. P1's partner cannot draw
$\ell_1 - \lambda'_1$ for a free $\lambda'_1$, since with weights known in preprocessing P1's conv masks are the
truncation's image of its prescribed triple share. So the other addend's P1 mask is committed as well: a
convolution producing it draws a PRF value in the image (uniform there, like a fresh mask, so the prescribed share
stays uniform), a ReLU producing it has committed bit-injection masks anyway (round~5). P1's committed mask of the sum
is then $\ell_1 = m_a + m_b$, exactly the mask the local addition gives, and the partner draws $m_a$, again in the
image. Which sums are committed follows from the network alone, so both parties agree on who sends what. This removes
the remaining 3.1\,MiB (ImageNet, every UC2 A2bits build with \flag{COMPRESS=0}: 3.21\,MB fewer received by P0, nothing
else changes); on the CIFAR ResNet50, whose every block has a residual sum (4 produced by a convolution, 12 by a
ReLU), the UC2 pass traffic falls from 16.8 to 12.3\,MB, and P1's check of every baked ReLU input passes with the real
weights. Convolutions now cost the A2B no message at all: in UC1 and UC2 only the stem's pooling output is remasked.

The round also fixes a leak in UC1: the committed masks were narrowed to the truncation's image in every build with
\flag{TRUNC_DELAYED=0}, but in UC1 P1's masks are free draws that hide the truncated share it sends, so a narrowed mask
revealed part of it (about one bit per value on average); only builds with weights known in preprocessing narrow now.
UC1's outputs do not depend on these masks and stay bit for bit the same. Neither change costs time: against
round~5, the 36 builds preprocess a median 0.01\s slower on Zen~4 ($-0.21$ to $+0.10$\s) and as fast on Zen~3
($-0.12$ to $+0.16$\s), and the online phase stays within 0.04\s. (An A/B series right after the change had put UC1's
A2bits RCA build 0.1--0.2\s behind round~5, all of it in P1's OT setup; in the final series the identical binary ran
0.05--0.1\s \emph{faster} than round~5, so that was series-to-series variation, not the change.)

\paragraph{Round 7.}\label{sec:triadround7} The bake's runtime and one more privacy fix.
\begin{enumerate}\itemsep1pt
\item \textbf{Repeated committed masks.} The counter-mode PRF behind the committed masks (the mask-only forward's
  truncation masks since round~4, every committed ReLU output mask since round~5, UC2's residual masks of round~6)
  took its block index and slot as $k / \mathrm{BUFFER\_SIZE}$ and $k \bmod \mathrm{BUFFER\_SIZE}$ of a macro without
  parentheses: $k / 512 / 32$ and $(k \bmod 512) / 32$. Each value came back for 32 consecutive masks, 16 distinct ones
  per 16,384, so each committed mask hid many values and the other party saw differences of secret activations. Masks
  never change the work, so no timing, traffic or accuracy number was affected; it showed when the commitment below drew
  from the same PRF and P1's narrowed UC2 masks came out tiny (SecureML truncation wraps, 0--2 of 10). The macro is
  parenthesized, and the PRF checks its outputs before the committed masks are drawn. The CIFAR outputs of all builds
  with committed masks change; all 18 classify 3--7 of 10.
\item \textbf{Baked A2B on the pool.} The baked A2B read $[c]$ through one global cursor, so its prepare and complete
  levels ran serially, where the unbaked A2B runs them on the worker pool. Each value now reads its slices by index.
\item \textbf{Parallel commitment.} The committed masks come from the PRF by slot, on 16 threads, in the OT phase.
\end{enumerate}
Against round~6, preprocessing is unchanged (median $\pm 0.00$\s on Zen~4, $-0.01$\s on Zen~3) and the online phase a
median 0.01\s and up to 0.10\s faster.

\paragraph{Round 8.}\label{sec:triadround8} The bake's Boolean addition, a ripple-carry adder of the two parties'
private inputs with one AND (two random OTs, one per direction) per bit and value, took 1.44--1.52\s of the A2bits
builds' preprocessing on flare / polynize. A per-round log showed where: each of its 31 dependent rounds generated its
own random OTs, split per OT worker into chunks of about 250,000 values, each with its own round trip, and every few
rounds the ferret instances ran dry and a whole extension round fell into the dependent chain.
\begin{enumerate}\itemsep1pt
\item \textbf{Random OTs first} (\flag{A2B_ADDER_BATCH}). The random OTs do not depend on the inputs, so all rounds'
  OTs are generated before the first round, in one call per OT pack and direction, starting next to the masks'
  commitment; the extension round then runs at full parallelism and outside the chain. A round only exchanges its two
  correction bits per AND (in four messages) and computes the shares; the adder's loops run on bit-position-contiguous
  arrays (the value-major layout had a stride of 32 words and took longer than the exchanges). The 31 rounds now take
  0.1\s together.
\item \textbf{The cut in the adder} (\flag{A2B_ADDER_CUT}). Under \flag{CUT_FRACTIONAL_BITS_OPT} every A2B replaces the top
  \flag{FRACTIONAL} slices of $[c]$ by the constant 0, so the Boolean addition stops after bit $\ell - F - 1$: 26
  instead of 31 AND rounds and 16\% fewer OTs. It applies only if every conversion of the network takes the cut, which
  the INIT pass records; in these networks all A2B inputs are ReLU inputs.
\end{enumerate}
At the same code with the two flags off and on (median of two runs, Zen~4), the nine \flag{COMPRESS=0} A2bits builds
preprocess 0.45--0.75\s faster (3.19--5.14 instead of 3.46--5.73\s), the \flag{COMPRESS=1} ones 0.05--0.12\s, and the
online phase does not change. The Boolean addition is now its OT volume: 1.04--1.21\s, of which about 1.0\s are the
random OTs (one extension round of all 64 ferret instances and the hashing) and 0.1\s the rounds. All A2bits builds
still classify 4--7 of 10 CIFAR-10 images, and multi-batch (192 images) 134 (\flag{MODELWEIGHTS_KNOWN=0}) and 124 (=1).
These are Zen~4 numbers only (algofi / goracle were booked).

\paragraph{Reduced-slack truncation.}\label{sec:triadts1} ABY2 now runs the reduced-slack truncation TS1 of
Truncation Untangled (its Fig.~9) fused into the ReLU: \flag{TRUNC_APPROACH=4} (TS\_Mix: TS1 in the ReLUs, the
probabilistic TS\{L\} elsewhere) and \flag{TRUNC_APPROACH=1} (TS1 also for the poolings, whose division joins the next
ReLU's TS1), both with \flag{TRUNC_DELAYED=1} and the A2B bake. In 3PC the party that holds the mask computes TS1's
mask-side values; in ABY2 nobody does, but their inputs are the carries of the two mask shares' sum, which the bake's
Boolean addition already computes. Two narrow COTs per value make the carries arithmetic, and a narrow multiplexer
gives the bit injection its one extra product; the public side (the masked value's top bits and its MSB) is local, so
the truncation sends nothing online.
\begin{enumerate}\itemsep1pt
\item \textbf{The cut in the Boolean addition.} Literally, TS1 needs the carry into the top bit, so the Boolean addition
  would run full width. Instead it adds the shares shifted locally by $F$ (a pooling's $1/d$ folded in) over
  $\ell - F$ bits, which keeps round~8's cut (26 instead of 31 rounds); the A2B converts the truncated value with the
  cut as well, and TS1 runs in the ring $2^{\ell-F}$. The dropped low carries are compensated by rounding the public
  side: the result is off by $-1$, 0 or $+1$ from the floor, with mean $+0.03$ LSB from the real value. The exact
  low carry (\flag{TS1_LOW_CARRY}, 0 or $+1$ as in 3PC) costs a full-width addition and a 31-bit COT per value; only the
  poolings' ReLUs take it, whose small averages need it.
\item \textbf{The cut for UC3's TS\{L\}} (\flag{A2B_DELAYED_CUT}). With public weights TS\{L\} delays the
  truncation to the ReLU, whose A2B therefore converted the untruncated value, without the cut. The same shifted
  addition gives it the cut: 245 fewer online rounds and 10.8\,MiB less online traffic for RCA, and 21--110\,MiB less
  preprocessing traffic. The reshared builds have no bake; there each party shifts its own additive share of the
  A2B input by $F$ (their sum is the truncated value minus 0 or 1): RCA 245 fewer rounds and 16.1\,MiB less online,
  PPA 24.7\,MiB, PPA4 9.6\,MiB. With the cut PPA4 computes 30--46\,ms longer online in every build, although it sends
  less; preprocessing and online together are still shorter.
\end{enumerate}
\Cref{tab:ts1} shows the ImageNet costs. TS\_Mix and TS1 need the bake, so they apply to the nine A2bits configs
without \flag{COMPRESS}; the others keep TS\{L\}. TS\_Mix sends the same online and 36--39\,MiB more in preprocessing
(the first version, with a full-width addition, 57--58\,MiB), 0.07--0.36\s more preprocessing time; TS1 removes the
last pooling's message. Online, all three take the same time, once the bit injection computes TS1's public side from
the A2B's input instead of storing it per value (that cost 0.02--0.04\s). Since TS1 has no wrap failures,
\flag{FRACTIONAL} can grow, and the cut adder shrinks with it: TS1 with $F = 8$ runs 148 fewer online rounds than
TS\{L\} with $F = 5$ (RCA; PPA 13.6\,MiB less online and 0.5\s less preprocessing) and classifies like the plaintext
model on CIFAR-10 (\cref{tab:ts1acc}), where TS\{L\} loses 20--50 images of 256 at $F = 8$ and collapses at $F = 10$.
(TS\_Mix divides a pooling before a ReLU, as in the ImageNet ResNet's stem, probabilistically at scale $2^{3F}$, which
wraps at $F \ge 8$; TS1 folds it into the ReLU.) At $F = 5$ all variants classify 156--166 of 256, the fixed point's
precision being the limit.

\paragraph{Exact truncation.}\label{sec:triadte} ABY2 had no exact truncation: the generic TE0 (A2B, shift, B2A) and
TE1 (Fantastic Four's carry correction) need B2A and share-level truncation primitives it does not implement. Both now run
fused into the ReLU on TS1's machinery (\flag{TRUNC_APPROACH=2} / \flag{=3}, \flag{TRUNC_DELAYED=1}, the A2B bake), exact
and without a message of their own. With $z = m + \nu$ and $a = m \bmod 2^F$, TS1's full design (with the low carry
$w_t$ of the mask shares and the offset $2^{\ell-1}$) yields $\lfloor z / 2^F \rfloor + [a \neq 0] - c_t$ for $z \geq 0$,
where $c_t$ is the carry into bit $F$ of $m + \nu$ and $[a \neq 0]$ is public. Only $z \geq 0$ matters, since DReLU
zeroes the rest, so the wrap of $m + \nu$ is linear there and, unlike in 3PC, no slack is needed. $c_t$ is the MSB of an
$(F + 1)$-bit a-known adder of $(0, a)$ and $(0, \nu \bmod 2^F)$, that is of $\mathrm{bool}(m)$ and the bake's $[c]$,
which runs in the same rounds as the ReLU's adder; with $c_t = m_c \oplus \lambda_c$ it enters the bit injection
linearly, from $[\lambda_c]$ (one COT) and $[\lambda_b \lambda_c]$ (one multiplexer) per value. The two differ in
DReLU: TE1 takes it of $A = \lfloor m/2^F \rfloor + \lfloor \nu/2^F \rfloor = \lfloor z/2^F \rfloor - c_t$ with the
cut (the two values differ only where the output is 0 either way), TE0 of $z$ at full width, exact for every $z$. Online,
TE1 costs TS1 plus the low adder's $F$ AND gates per value; TE0 adds the rounds the cut saves. Every positive input of
the unit test (4,096 random values, $|v|$ up to $2^{31}$ for TE0 and $2^{30}$ for TE1) comes out exact, with all three
adders at 32 and 64 bits. On CIFAR-10, TE0 and TE1 compute the same values and classify 158 ($F = 5$) and 185 ($F = 8$)
of the 256 images in all three use cases; exact truncation floors (mean error $-0.23$ LSB), which costs nothing at
$F = 8$ (TS1 187, plaintext 189).

\Cref{tab:te} shows the ImageNet costs at the final code. TE1's online phase takes as long as TS1's (0.34--0.50 against
0.33--0.49\s) for 10.5\,MiB (RCA) or 21\,MiB (PPA, PPA4) more online traffic, the low adder's AND gates, and the same
rounds with RCA; its preprocessing grows by 0.1--0.8\s and 160--190\,MiB (the full-width Boolean addition, the COTs of

TE0's full-width DReLU costs 240 more rounds with RCA and up to 0.13\s of online time (PPA4).

\paragraph{What is left.} \Cref{tab:triadphases} splits the time of six builds at the final code; the ranges below are
over all 18 builds with \flag{COMPRESS=0}. With secret weights, preprocessing is now the OT phase (1.4--4.7\s, inside
the pass), the pass's own work (0.33--0.58\s, including its mask-only forward), the steps after it (0.22--0.56\s) and
0.1--0.3\s of key exchange, input preparation and gaps; the conv triples run alongside the OT phase and finish before
the pass does.
\begin{enumerate}\itemsep1pt
\item \textbf{OT generation} remains the largest cost. Every build pays 0.84--1.04\s to set up the 32 ferret packs (about
  0.1\s more with secret weights, whose conv triples run alongside); the tuples after that take 0.26--0.34\s for RCA but
  1.6--3.6\s for PPA4, whose Beaver 3- and 4-tuples need up to six more extension rounds of all 32 packs. In the round-3
  CPU profile, ferret's LPN step took 33--41\% of all samples, the AES key schedules of the correlation-robust hash
  8--11\%. The last extension round is only partly used, but that wastes at most one round (about 0.3\s for PPA4). A
  fixed-key hash would remove most of the key schedules, but that is a security decision (\cref{sec:limits}).
\item \textbf{The bake's Boolean addition} cost the A2bits builds 1.41--1.53\s: 31 dependent COT-multiplication rounds
  of 15--22\ms plus an extension round. Since round~8 it is 1.04--1.21\s, almost all of it the OTs it needs (two per
  AND); a log-depth adder would need fewer rounds but more AND gates, and so more OTs, and B2A of random bits halves the
  OTs but cannot give P1 the prescribed masks of UC2's residual sums.
\item \textbf{The conv triples} no longer show: in round~3 the HE ran 0.28--0.60\s past the pass (reshared PPA4:
  1.0--1.1\s, from P1's serial bake, fixed in round~4). Running alongside the OT phase, they compete with it for cores
  and memory bandwidth, which the longer OT setup shows.
\item \textbf{Serial work} in the pass: the GEMM levels (the weights-known-in-preprocessing path pushes into vectors
  there) and the bake's input preparation still run on one thread; with public weights the mask-only forward adds
  0.3\s to the A2bits pass (0.55--0.74 against 0.24--0.30\s).
\item \textbf{Online}, RCA's 1,714--2,012 rounds cost 0.16--0.19\s of waiting. Of the rest, the main thread spent
  0.11\s handing levels to the pool, 0.05\s transposing bits for the A2B serially, and 0.06\s in layer glue (copies,
  residual additions, freeing buffers) in the round-3 profile.
\item \textbf{Communication:} output repacking (round~4) removes 40\% of the conv-triple traffic at 1.3--1.7\s of
  CPU; it pays off below about 1.2\,Gbit/s (UC2) or 2.1\,Gbit/s (UC1). Of the bake's remask, only the stem's pooling
  output is left (1.5\,MiB, \cref{sec:limits}).
\end{enumerate}
